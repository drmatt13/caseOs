# GRAPHQL CONTRACT PROPAGATION

Use this as the human-readable map for how typed data moves from the database
to the React UI.

## Contract Flow

- **Prisma is the persistence contract**
  - `packages/database/prisma/schema.prisma` defines tables, fields, enums,
    relations, indexes, nullability, defaults, and database mappings.
  - Prisma migrations turn that schema into actual PostgreSQL structure.
  - Prisma client generation gives backend code typed database access.

- **Prisma generation is mostly automated**
  - The schema includes Prisma client generators for the environments where the
    client is used.
  - The project also generates Prisma/Pothos integration types from the Prisma
    schema.
  - This removes most of the manual work around client binaries and generated
    database types.

- **Pothos types help build the backend GraphQL schema**
  - The `prisma-pothos-types` generator writes:
    - `packages/database/src/generated/pothos.ts`
  - Backend GraphQL schema files import those generated Pothos Prisma types.
  - These types help Pothos understand Prisma model shapes while building the
    GraphQL schema.
  - They do **not** automatically expose every database field to GraphQL.

- **Pothos defines the real GraphQL API contract**
  - Backend schema files live under:
    - `cdk-app/lambda_functions/graphql-api/schema/`
  - These files define GraphQL object types, input types, queries, mutations,
    enums, resolver behavior, and GraphQL nullability.
  - This is where the backend decides what the frontend is allowed to query or
    mutate.

- **GraphQL Yoga serves the Pothos-built schema**
  - The `graphql-api` Lambda uses GraphQL Yoga.
  - Yoga receives the schema built by Pothos.
  - Requests go through the Lambda, session/auth context, Prisma context, and
    then into the Pothos resolvers.

- **GraphQL Codegen bridges backend schema to frontend types**
  - Root `codegen.ts` imports the executable backend schema directly from:
    - `cdk-app/lambda_functions/graphql-api/schema/index`
  - Running `npm run codegen` scans frontend GraphQL documents in:
    - `client-app/src/api/**/*.ts`
  - It generates frontend GraphQL artifacts in:
    - `client-app/src/api/generated/`
  - It also writes the schema snapshot:
    - `client-app/src/api/generated/schema.graphql`

- **Frontend GraphQL documents define exact operation shapes**
  - Feature API folders define query and mutation documents in `operations.ts`.
  - Documents use the generated `graphql(...)` helper.
  - The generated operation type only includes fields selected by that specific
    query or mutation.
  - Example: `GetCurrentUserQuery` is the result shape of the `GetCurrentUser`
    document, not the full backend `CurrentUser` object type.

- **The custom frontend GraphQL client preserves generated typing**
  - `client-app/src/api/graphql/client.ts` exposes `executeGraphQL(...)`.
  - It accepts typed GraphQL documents:
    - `TypedDocumentNode<TData, TVariables>`
  - Because `graphql(...)` returns a typed document, `executeGraphQL(...)` can
    infer result and variable types.
  - Raw GraphQL result and variable types are already generated by codegen.

- **Manual frontend return types are optional**
  - You do **not** need manual return types just to get GraphQL typing.
  - Define manual model/result types when the frontend reshapes or stabilizes
    the generated GraphQL result.
  - Good reasons to add frontend model types:
    - normalize nullable generated fields into app defaults
    - add derived values
    - convert dates or IDs into a frontend-friendly shape
    - hide backend payload nesting from UI components
    - keep UI code stable while GraphQL documents evolve

- **React Query wraps frontend API operations**
  - `operations.ts` owns GraphQL documents, raw API calls, and normalization.
  - `hooks.ts` owns `useQuery`, `useMutation`, query keys, and cache
    invalidation.
  - UI components should usually import hooks from the feature API folder.
  - UI components should avoid importing raw GraphQL operations unless there is
    a deliberate non-React use case.

## Current User Example

- `client-app/src/api/currentUser/operations.ts`
  - Defines `GetCurrentUserDocument` and `UpdateCurrentUserDocument`.
  - Calls `executeGraphQL(...)`.
  - Throws app-level errors when required payloads are missing.
  - Normalizes returned users before giving data to React Query.

- `client-app/src/api/currentUser/model.ts`
  - Imports generated GraphQL types such as `GetCurrentUserQuery` and
    `AccountTier`.
  - Derives raw payload types from generated operation results.
  - Defines stable frontend types like `CurrentUser` and
    `GetCurrentUserResult`.
  - Adds app defaults and profile-picture cache versioning.

- `client-app/src/api/currentUser/hooks.ts`
  - Exposes `useCurrentUserQuery`.
  - Exposes `useUpdateUserMutation`.
  - Owns the `currentUserQueryKey`.
  - Invalidates current-user cache after successful user updates.

## When The Contract Changes

- **New database field**
  - Update Prisma schema.
  - Create/apply migration.
  - Regenerate Prisma and Pothos types.
  - Expose the field intentionally in Pothos if it belongs in the API.
  - Add the field to frontend GraphQL documents if the UI needs it.
  - Run codegen.
  - Update frontend model normalization only if needed.
  - Update hooks/UI usage.

- **New mutation**
  - Add Prisma write logic or service logic.
  - Add Pothos input and mutation field.
  - Validate resolver input and auth/ownership behavior.
  - Add frontend mutation document.
  - Run codegen.
  - Add operation function and mutation hook.
  - Invalidate or update the smallest useful React Query cache key.

- **Nullability change**
  - Decide whether database nullability and GraphQL nullability should match.
  - Update Pothos field/input nullability intentionally.
  - Run codegen.
  - Fix frontend guards, defaults, and empty states.

- **Enum change**
  - Update Prisma enum.
  - Migrate/regenerate.
  - Expose/update Pothos enum.
  - Run codegen.
  - Update frontend labels, conditionals, and fallbacks.

## Key Correction

- GraphQL Codegen already generates query and mutation result types.
- Manual frontend result types are only needed when the app reshapes,
  normalizes, narrows, or stabilizes the generated GraphQL result.
